## 职业目标与路线选择

> **一句话战略：** 保留 CAE / 图形工程的技术基本盘，用机器人仿真与物理系统能力实现职业升级；智能家居解决生活问题，自媒体传播作品，而不是反过来决定学习方向。

### 不可改变的条件

- 工作地点：长沙常驻；不考虑北上深等地异地迁居。
- 职业排序：更优技术岗位 > 技术影响力 > 个人软硬件产品收入。
- 能力迁移：不从初级工程师重新起步，持续强化 C++ / GPU / 工程架构优势。
- 投入边界：保持在职转型；合理分配业余时间，不以长期熬夜为代价。

### 两条方向如何分工

| 维度 | 职业主线｜机器人仿真 / 数字孪生 | 个人实践｜AIoT / 智能家居 |
| --- | --- | --- |
| 目标 | 获取更高价值的研发岗位；提升系统技术深度 | 改善新家生活；打通实体设备控制 |
| 核心技术 | C++、Python、ROS 2、MuJoCo、USD、物理/传感器仿真 | 米家、Home Assistant、MQTT、ESP32、3D 打印 |
| 最重要的成果 | 可复现、可测试、有性能数据的专业项目 | 家人稳定可用的语音和自动化场景 |
| 使用原则 | 作为履历的技术核心 | 不强求商业化，不占用主线过多精力 |

### 目标岗位优先级

| 顺序 | 优先投递方向 | 判断岗位是否值得 |
| --- | --- | --- |
| A | 机器人仿真平台 / 仿真引擎 C++ 工程师 | 有物理仿真、机器人模型、数据/场景架构或性能优化工作 |

### 季度复盘时只检查四件事

- 作品能否在另一台电脑上按文档复现，而不是只在自己的开发环境中运行。
- 是否开始处理物理与控制闭环，而不仅是三维动画与界面。
- 是否积累明确的工程指标：物理步进耗时、状态采样吞吐、延迟、资源占用或错误率。
- 当前学习内容是否能对应长沙真实岗位描述；如果不能，及时调整而不是继续追热点。

> **路线切换原则：** 如果 6 个月内本地机器人仿真岗位样本较少，就暂时加强机器人 C++ / 工业 3D 视觉，同时保留 CAE / GPU 岗位通道。不要把职业选择押在单一“具身智能”标签上。

## 核心作品：RoboSim Workbench

项目定位：面向开发者的机器人仿真与状态分析工具。它不是从零实现物理引擎，也不是单纯的机器人动画播放器，而是复用 MuJoCo，开发能用于仿真调试、数据分析和性能评估的工程系统。

> **技术架构建议：** MuJoCo 负责动力学时间步与接触求解；Python/C++ 负责控制和数据接口；ROS 2 负责标准机器人通信；Qt + OSG 或轻量可视化层负责交互展示；日志与测试模块提供可复现证据。

### 最低可交付版本（MVP）

- 加载一个公开的机械臂模型（建议先做固定机械臂，避免过早陷入复杂全屋导航）。
- 实现关节控制或末端目标跟踪；显示关节状态、轨迹与接触事件。
- 记录时间步状态与控制输入，支持暂停、回放和导出。
- 提供至少两项自动化测试：模型加载与控制结果检查。
- 运行基准测试，给出硬件、模型规模、仿真步长和实测结果。

### 作品进阶方向（从中选一个深挖）

| 深入方向 | 具体可做的工程问题 | 对应职业价值 |
| --- | --- | --- |
| 仿真性能 | 多机器人并发、多场景加载、状态提取和可视化解耦 | 仿真基础设施 / 性能工程 |
| 数据平台 | 高频关节数据、轨迹查询、测试回放和一致性验证 | 机器人训练评测 / 数据系统 |
| 场景与感知 | URDF/MJCF 模型、传感器配置与场景资源组织 | 数字孪生 / 传感器仿真 |
| 3D 视觉 | 点云可视化、空间结构、碰撞几何和感知数据调试 | 长沙工业视觉 / 机器人岗位 |

### 专业作品必须附带的材料

**交付材料：**

- ① GitHub 源码与构建指南
- ② 系统架构图
- ③ 1–3 分钟演示视频
- ④ 自动测试说明
- ⑤ 性能报告（注明硬件与测试条件）
- ⑥ 问题复盘与优化取舍。

**成功标准：** 招聘方看到仓库，不只是认为“你会用 MuJoCo”，还能够判断你具备复杂 C++ 系统的设计、调试与性能优化能力。

## 生活实践与技术传播

### 家庭项目：Home AI Hub

目标是改善新家的日常体验，不追求自己造一套完整家居平台。以现有米家设备、小爱语音、Home Assistant 为主，必要时增加 ESP32 与 3D 打印结构件。

| 阶段 | 建设内容 | 完成标准 |
| --- | --- | --- |
| 第一步｜直接见效 | 灯光、窗帘、空调、投影幕布的现成设备控制 | 家人能直接语音使用；保留物理开关 |
| 第二步｜系统集成 | Home Assistant 设备状态、场景规则、日志与失败反馈 | 离线和误操作有处理方案；可查看错误日志 |
| 第三步｜自制扩展 | ESP32 低压传感器、定制外壳、智能场景按钮 | 稳定运行一个月并留下源码与安装说明 |

> **安全边界：** 市电接线交给合格电工；智能幕布必须匹配专用电机控制方式；保留原有手动控制；不把未经验证的大模型决策用于高风险家电操作。

### 技术自媒体：一份研发，三种产出

| 渠道 | 主要内容 | 要证明的价值 |
| --- | --- | --- |
| GitHub | 完整代码、README、架构、性能、测试、演示资料 | 技术能力可验证、可复现 |
| B 站 | 机器人运动、仿真结果、真实智能家居改造、性能对比 | 直观展示系统结果，积累受众 |
| 知乎 / 公众号 | 工程取舍、技术原理、失效分析、学习路线 | 形成可被搜索和引用的专业认知 |

## 岗位筛选、风险与启动清单

### 跳槽决策规则

先设硬性门槛：常驻长沙；研发办公地点与通勤可接受；工作内容属于真正的研发而非长期驻场实施。满足后，再按下表比较岗位。

| 比较项 | 建议权重 | 要问清楚的问题 |
| --- | --- | --- |
| 技术深度与积累 | 30% | 是否接触 C++ 核心、物理/仿真、系统性能、ROS 2/感知等实质问题？ |
| 薪酬与总回报 | 25% | 税前年薪、奖金、加班、社保公积金和长期发展是否真正提升？ |
| 发展空间 | 20% | 团队有无中长期产品？架构责任与技术影响是否有增长？ |
| 团队与产品确定性 | 15% | 业务真实度、研发质量、人员稳定性和项目持续性如何？ |
| 生活与通勤成本 | 10% | 日常通勤、出差强度、时间边界是否与定居生活兼容？ |

### 需要主动规避的风险

- 为了“具身智能”标签而从技术核心岗位换到展示型/集成型岗位。
- 同时学习机器人、嵌入式、AI 大模型、硬件设计等过多分支，导致没有一项成果足够深入。
- 为家居项目重写成熟系统，把大量时间花在设备兼容和家人日常维护上。
- 没有明确作品证据就急于跳槽，或仅因为行业热度就接受更差的工作条件。
